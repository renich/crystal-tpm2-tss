crystal-tpm2-tss: Crystal-Native TPM 2.0 Software Stack
=======================================================

Purpose
-------

The ``crystal-tpm2-tss`` project provides a robust, native Crystal implementation of the Trusted Platform Module (TPM) 2.0 Software Stack (TSS). It bridges the gap between high-level Crystal applications and low-level TPM 2.0 hardware, enabling secure cryptographic operations, key management, and persistent credential storage. A primary use-case addressed by this stack is the implementation of FIDO2/CTAP2 authenticators, where hardware-backed keys and non-volatile storage are paramount for security.

By offering a native Crystal abstraction, the project removes the need for complex C-bindings to existing TSS libraries while maintaining strict compliance with the TCG TPM 2.0 Library Specification. It encapsulates complex TPM concepts like session management, authorization, parameter encryption, and NV (Non-Volatile) index allocation behind safe and intuitive APIs.

Architecture
------------

The architecture of ``crystal-tpm2-tss`` is designed to ensure strict separation of concerns, reliable session state management, and isolation from hardware dependencies for testing.

Hardware Abstraction
~~~~~~~~~~~~~~~~~~~~

To ensure testability and reliable Continuous Integration, the stack abstracts hardware interactions through a ``TPMDevice`` class. This abstraction simulates binary TPM responses, isolating protocol parsing and logical state transitions from actual D-Bus or character device communication. This allows for rigorous automated testing of edge cases without requiring physical TPM hardware.

Session Management
~~~~~~~~~~~~~~~~~~

Secure communication with the TPM necessitates rigorous synchronization of session state. The stack's session components manage nonce rolling, HMAC computations, and response authorization parsing. By tracking the TPM nonce (``nonceTPM``) and caller nonce (``nonceCaller``) accurately, the system prevents replay attacks and ensures command authenticity. The ``CONTINUESESSION`` flag is employed as the default behavior to maintain active sessions efficiently across multiple commands.

NV Storage for Persistence
~~~~~~~~~~~~~~~~~~~~~~~~~~

To support persistent FIDO2 credentials and Key Derivation Function (KDF) keys across system reboots, the stack integrates with the TPM's Non-Volatile (NV) storage capabilities. This allows the system to store essential metadata and derivation roots securely within the hardware boundaries, avoiding the fragility of per-boot ephemeral keys.

Cryptography
------------

The stack employs state-of-art cryptographic primitives and mechanisms defined by the TPM 2.0 specification to protect data in transit and at rest.

Parameter Encryption
~~~~~~~~~~~~~~~~~~~~

Certain commands and responses exchange sensitive parameters (such as raw key material or auth values) that must be protected over the local interface (e.g., D-Bus). The stack implements KDFa-based symmetric encryption to secure these parameters. It derives unique encryption keys using the TPM 2.0 KDFa algorithm with ``nonceTPM`` and ``nonceCaller`` as context, applying AES-CFB or XOR obfuscation as negotiated in the session attributes.

Collision-Resistant Derivation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

FIDO2 credential creation requires predictable, non-overlapping NV indices. The stack implements a collision-resistant allocation mechanism by employing a full 32-bit SHA-256 hash of the credential ID. It combines this base index with linear probing, verifying embedded credential IDs to resolve collisions deterministicly without data loss.

Safety Guarantees
-----------------

The project provides robust safety guarantees against both logical and hardware-induced vulnerabilities.

ECDSA Nonce Reuse Detection
~~~~~~~~~~~~~~~~~~~~~~~~~~~

The ECDSA algorithm is catastrophically vulnerable to random number generator (RNG) failures. If a TPM's hardware RNG fails and reuses a nonce (the ``k`` value) for two different signatures, the private key can be trivially recovered. To mitigate this risk, ``crystal-tpm2-tss`` incorporates a ``SignatureRTracker``. This component monitors the ``r`` values (derived from the nonce) of all ECDSA signatures generated by the hardware. It actively detects and rejects duplicate ``r`` values, thereby protecting the underlying keys even in the event of a catastrophic hardware RNG failure.

Deterministic Authorization
~~~~~~~~~~~~~~~~~~~~~~~~~~~

Authentication values are deterministically derived using established KDFs, ensuring that authorization state cannot be lost or compromised due to weak random generation. The stack enforces strict policy and password authorization areas for all sensitive commands, preventing unauthorized use of loaded keys or NV indices.

Testing & Proof of Functionality
--------------------------------

The ``crystal-tpm2-tss`` stack relies on rigorous unit and integration testing to ensure correctness and safety. According to the latest test reports, the implementation successfully achieves 100% test coverage across 26 scenarios. 

Key validation areas include:

- **Cryptographic Algorithms**: Parameter encryption using KDFa XOR, proper HMAC computations, and deterministic authorization value derivation.
- **Hardware Abstractions**: A mock ``TPMDevice`` effectively simulates TPM hardware, allowing for thorough evaluation of edge cases and device communication logic.
- **State and Session Tracking**: Sessions reliably initialize with ``CONTINUESESSION``, and nonces are correctly extracted and rolled. Crucially, the ``SignatureRTracker`` correctly adds, tracks, and prunes ``r`` values to prevent nonce reuse in ECDSA signatures.
- **Key and Credential Management**: The ``KDFKeyManager`` successfully handles the creation and persistent storage of KDF keys within TPM NV, even properly mitigating NV index collisions. The ``FIDO2CredentialManager`` seamlessly performs end-to-end credential creation and signing.

The test suite also confirms robust handling of edge cases, including gracefully managing failures during primary key creation or signature processes, as well as correctly identifying corrupted or incomplete Non-Volatile (NV) read responses.
