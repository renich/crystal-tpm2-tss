Architecture
============

This document outlines the key architectural decisions for the TPM 2.0 Stack.

TPM NV for KDF Persistence
--------------------------

**Why:** The Key Derivation Function (KDF) key must survive system reboots to maintain persistent credentials.

**Trade-off:** This introduces the complexity of managing TPM Non-Volatile (NV) storage, but is necessary compared to the broken approach of using a random key per boot.

Hardware Abstraction for Testing
--------------------------------

**Why:** To ensure greater than 80% code coverage and reliable Continuous Integration, hardware dependencies must be isolated.

**Decision:** A mock ``TPMDevice`` class abstraction simulates TPM binary responses, separating protocol parsing and logic from actual hardware communication.

Session Management and Nonce Tracking
-------------------------------------

**Why:** Secure communication with the TPM requires rigorous synchronization of state.

**Decision:** Session components manage nonce rolling, HMAC computations, and parse response authorization areas to track the TPM nonce. The ``CONTINUESESSION`` flag is used as the default behavior to maintain active sessions.

Parameter Encryption
--------------------

**Why:** Certain commands and responses contain sensitive parameters that must be encrypted over the D-Bus interface.

**Decision:** The stack implements KDFa-based symmetric encryption for securing command and response parameters.

Collision-Resistant NV Indices
------------------------------

**Why:** FIDO2 credential creation needs predictable but non-overlapping indices in TPM Non-Volatile storage.

**Decision:** The credential manager uses a 32-bit hash mechanism combined with probing to determine collision-resistant NV indices for storing persistent key data.

ECDSA Nonce Reuse Detection
---------------------------

**Why:** ECDSA is extremely vulnerable to random number generator failures leading to nonce reuse, which immediately leaks the private key.

**Decision:** A dedicated ``SignatureRTracker`` monitors the ``r`` values of all ECDSA signatures generated by the TPM, instantly rejecting duplicate values to protect the underlying keys.
